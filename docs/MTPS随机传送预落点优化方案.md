# MTPS 随机传送预落点优化方案（接入 ZXDash 群系图）

> 状态：**设计稿，未动代码**。文中所有「现状」都标了出处（文件 + 行号），所有「结论」区分了
> 「已核实」与「待探针验证」。第 9 节是需要你拍板的几个点，第 11 节是动手前先跑的验证。

---

## 0. 一句话结论

MTPS 现在**只能对「存档里已经生成过的地形」预计算落点**，没生成过的地方只能等引擎现场生成
（`LOAD_CHUNK` 等待）。而 ZXDash 的群系底图背后是 **cubiomes-bedrock：拿世界种子就能算出任意坐标的
群系 ID 和近似地表高度**，完全不需要存档、不需要地形生成。把这份能力接进 MTPS，就能在开服阶段
把「未生成区域的预落点」也预先算出来（默认 3000 个），随机传送时优先命中这些点，**把"随机到处乱撞"
变成"命中已知候选点 + 只等必要的区块加载"**。

顺带解决三个现有弱点：群系排除（不再往大洋里传）、预落点池持久化后**只补缺口不重扫**、超大半径
（如 3000000）保存配置后**静默重建未加载类预落点并替换一半旧点**。

## 1. 需求拆解

| 你的原话 | 落成什么 |
| --- | --- |
| mtps 可以读取 ZXDash 的群系地图 | 复用 ZXDash 的 cubiomes-bedrock（同库同种子同版本映射）。详见 §3、§4.1 |
| 首先是群系排除，排除掉那些海洋群系什么的 | 预落点生成时按群系 ID 排除海洋 / 河流（可配），另加"邻域一致性"避免落在群系边界。§4.4 |
| 扫存档的预落点是直接随机坐标扫存档内随机的地点扫上预设的 1000 个 | 改成**预落点池**：已加载类（存档内）默认 1000 个 + 未加载类（存档外）默认 3000 个，均为 config 可调。§4.3 |
| 而群系地图看看能否提升到预计算大致地形，做预落点的处理 | **能**。cubiomes 除群系外还给近似地表高度 `mapApproxHeight`，用它给未加载类的点算 `approxY`。§3.1、§4.5 |
| 玩家随机传送是优先随机出大致的区域，检查是否有预落点在 500 格范围内 | 池命中路径：抽一个池点 → 在其 500 格邻域抖动出实际落点 → 走现有判定。§4.6 |
| 如果有则直接加载并传送到预落点 | 已加载类命中的点走落点表 → 零 IO 直判 → 只等区块**载入**（不生成）。 |
| 如果没有则走降级策略 | 完全保留现有四级数据源链路，一行不改。§4.6 |
| 整套行为只能有开服加载和部分逻辑等待区域块加载的等待时间 | 设计不变量：**传送路径上不做群系计算、不做存档 IO**；cubiomes 全部在开服后台算完落盘。§4.9 |
| 预计算点保存后不能让其再开服就乱扫，需要的是扫上缺少的数量 | 池落盘 + `.meta` 指纹；开服只算 `目标数 − 现有有效数` 的缺口。§4.7 |
| 预设为已加载区域块 1000 个传送点，未加载区域块 3000 个（config 可调） | `pool.loadedTarget` / `pool.unloadedTarget`。§5 |
| 预设范围过大例如 3000000，保存配置之后静默随机出预落点（未加载区域） | 半径变更 → 打标记 → 后台按新半径重算未加载类。§4.8 |
| 并且替换掉原本已经算好的未加载区域的一半 | `pool.replaceRatio` 默认 0.5：新点入池时淘汰一半旧点，保留一半。§4.8 |

**术语对齐**：你说的「预落点」= 代码里的「落点表 / 落点预计算」（`BedrockLevelReader::Landing`）。
本文统一叫**预落点**，池子叫**预落点池**。

## 2. 现状（代码事实）

### 2.1 MTPS 的四级数据源

`RandomTeleport.cpp` 会话状态机：`选点 → PROBE → (LOAD_CHUNK) → SCAN_CHUNK → (EXPAND) → 传送/退款`。
判定落在 `resolveChunk()`（`SurfaceScan.cpp:232`），按代价从低到高：

| 级 | 来源 | 代价 | 出处 |
| --- | --- | --- | --- |
| ① | 内存里的区块（数据最新） | ~1ms/块 | `SurfaceScan.cpp:244` |
| ② | 落点预计算表（内存二分） | 零 IO | `SurfaceScan.cpp:251` |
| ③ | 直读存档 `.ldb` | 读盘 + 解压 | `SurfaceScan.cpp:272` |
| ④ | 登记临时常加载区域让引擎生成 | 数十~数百 tick | `stepProbe` 的 `NoData` 分支 `RandomTeleport.cpp:556` |

③ 返回 `NoData`（表已就绪但查不到 = 存档确实没这块地）就走 ④：`requestChunkLoad` +
`ensureTickingArea` → `LOAD_CHUNK` 轮询等就绪（`RandomTeleport.cpp:565`），单落点上限
`RTP_CHUNK_WAIT_TICKS = 200` tick。

**这就是你说的"部分逻辑等待区域块加载的等待时间"** —— 目前它只发生在 ④，而 ④ 是没生成过的地形的唯一出路。

### 2.2 现有落点预计算表

`ArchiveScanner`（`ArchiveScanner.cpp`）开服后后台线程：等待 45s（`RTP_LANDING_DEFER_SECONDS`）
→ `BedrockLevelReader::open()` 建 `.ldb` 索引 → `buildLandings()`（`LandingScan.cpp:118`）逐 chunk
算**一个**安全落点 → 落盘 `Meowdata/Mtps/landings.cache` + `.meta`（存 `.ldb` 指纹 + maxLandings）。

实测现状：`landings.cache` = 21012 B，`Landing` 16 B/条，表头 36 B → **主世界 1311 个 chunk**
（nether/end 为 0）。世界本身 27 MB。`.meta` 命中的前提是 `.ldb` 指纹不变，否则整轮重算。

**注意 2 个事实**（决定了优化方向）：

1. **表的规模 = 存档规模**，与预设半径无关。你这个存档 1311 条，而运行时配置
   `randomTeleport.presets[0].radius = 500000`。半径和表的实际覆盖范围完全不匹配。
2. **选点用的是拒绝采样**（`LandingScan.cpp:409` `pickSafeLandingInRange`）：从**整张表**随机抽一条，
   抽中再判是否在半径内，最多 128 次。表小的时候没事；**表一大、半径一小，绝大多数抽样都在圆外**，
   128 次用完直接返回 false（局部区域明明有点却挑不出来）。这是"扫存档预落点"最该修的地方。

### 2.3 ZXDash 群系图的真实机制（已核实）

`ZXDash.dll` 由 `plugins/ZXPanel/src/` 编译（`plugins/ZXPanel/bin/ZXDash/` 是构建产物），
群系底图在 `src/mod/BiomeBackground.cpp`：

- 库：**cubiomes-bedrock**（`plugins/ZXPanel/third_party/cubiomes/`，基岩版分支：群系 ID 表 /
  版本断点 / 种子派生均按基岩实现）。
- 种子：`lvl->getLevelSeed64().mValue`（**完整 64 位**，`ZXPanel.cpp:12749`；游戏内显示的只是低 32 位）。
- 版本映射：`mcForVersion(major, minor, patch)` → cubiomes `MCVersion`；本服 = `MC_26_40`（mc=28，
  磁盘上的瓦片目录名 `s-6197444756905386890_m28_r0_v7` 正好对上）。
- 生成：`setupGenerator(g, mc, 0)` + `applySeed(g, 0, seed)`，`genBiomes` 取群系格（scale=4），
  **y=15（≈方块 y60，近海平面切片）**，颜色查 cubiomes 内置 `initBiomeColors()`。
- 瓦片：256×256 RGBA PNG，**rz 层每像素 2^rz 格，瓦片 (tx,ty) 覆盖方块区间
  `[tx·256·2^rz, (tx+1)·256·2^rz)`**（`BiomeBackground.h` 头注释）。
- 落盘：按需生成（HTTP 请求触发 → 后台队列 → 原子写），路径
  `unmined-web/biome/s<seed>_m<mc>_r<renderZoom>_v7/<rz>/<tx>_<ty>.png`。

## 3. 关键结论：群系图能给什么、不能给什么

### 3.1 能给（这才是接它的理由）

| 能力 | API | 说明 |
| --- | --- | --- |
| 任意坐标的群系 ID | `getBiomeAt(g, scale, x, y, z)` | `scale=1` 是方块坐标，`scale=4` 是群系格（`generator.h:88`）。**不需要存档、不需要生成地形** |
| 批量群系 | `genBiomes(g, cache, Range)` | 一次一块区域，带行缓存 |
| **近似地表高度** | `mapApproxHeight(y, ids, g, sn, x, z, w, h)` | `generator.h:135`：1:4 采样，**输出以方块为单位的近似高度**，同时回填群系 ID。MC ≥ 1.18 分支走 `sampleBiomeNoise`，`y = np[NP_DEPTH]/76.0`（`generator.c:610`） |

也就是说：**「预计算大致地形」这件事 cubiomes 本来就提供**，`mapApproxHeight` 就是为
"找平坦地 / 找出生点"这类需求做的。你要的"用群系图提升到大致地形"不是曲线救国，是直接调这个。

### 3.2 不能给（安全红线）

近似高度**不是**真实地形：洞穴、峡谷、玩家改造、结构（村庄/废弃矿井）、水体和群系图的采样误差
都不在里面。所以：

> **绝不允许用 `approxY` 直接传送。** 它只能用来 ① 提前淘汰明显不可用的候选点
> （高度低于海平面、或者落在排除群系），② 当扫描提示（`hintY`）加速生成后的真实地表扫描。
> 真实落点永远由生成后的 `findSurfaceSafe` / `findSafeInSurface` 决定。

`findSurfaceSafe` 本来就支持 `hintY`（`RandomTeleportInternal.h`，"提示只是加速：试不中就走完整流程"），
这条路是现成的。

### 3.3 为什么不能靠"读 PNG 瓦片"来实现

"MTPS 读取 ZXDash 的群系地图"如果理解成**读磁盘上那些 PNG**，有三个硬伤：

1. **覆盖是稀疏且随机的**：瓦片由浏览器请求触发（`enqueueBiomeTile`，`ZXPanel.cpp:17603`），
   磁盘上只有被浏览过的区域。当前 `unmined-web/biome/.../` 只有 rz ∈ {0,1,3..10} 共 499 张瓦片，
   rz=0 层只有 8×5 张 = 约 2048×1280 格。**拿它当 3000000 半径的数据源不可能**。
2. **远景瓦片被"平均"过**：`renderTile` 在 k≥3 时每像素做 N×N 面积平均（v7 的改动，见
   `BiomeBackground.cpp` 注释），边界像素是混色 —— 颜色反查群系 ID 不可靠。
3. **要自己解 PNG**：多一个 zlib 解码 + 颜色反查表（`initBiomeColors` 只有 ID→颜色，反向查要自建）。

**结论：把它当"校验/对照"可以（rz ≤ 2 时像素精确），当数据源不行。真正的数据源是瓦片背后的
cubiomes 生成器。** 好在 cubiomes 是同一份源码、同一个种子、同一个版本映射 —— "同源复用"等价于
读同一张图，但不受渲染覆盖和平均的影响。

## 4. 总体设计

### 4.1 群系采样器（MTPS 侧）

新增 `src/BiomeSampler.cpp/.h`，**独立翻译单元，禁引任何 MC/LL 头**
（cubiomes 的 `enum Dimension` 与 BDS 头冲突，`BiomeBackground.cpp:16` 已经踩过这个坑）。

```cpp
namespace mtps {
class BiomeSampler {                       // 单例 + 一把锁；生成器按线程隔离（thread_local）
public:
    void  configure(uint64_t seed, int cubiomesMc);   // 种子/mc 变更时重建
    bool  ready() const;
    int   biomeAt(int blockX, int blockZ);            // cubiomes 群系 ID；-1 = 失败
    bool  approxHeight(float& y, int& biomeId, int blockX, int blockZ);
    bool  neighborAgree(int blockX, int blockZ, int r, int& biomeId);  // r×r 邻域群系一致
    int   mc() const;                                 // 诊断/指纹用
};
}
```

- 种子来源与 ZXDash **同一个调用**：`ll::service::getLevel()->getLevelSeed64().mValue`。
- mc 映射**照抄 `mcForVersion`**（避免两份实现漂移）；建议直接把 ZXPanel 的
  `third_party/cubiomes/` 整目录拷进 Mtps 源码树，与 ZXDash 保持同一 commit。
- 采样切片与 ZXDash 底图一致：**scale=4, y=15**（≈方块 y60），这样"地图上看是海"和
  "MTPS 判定是海"完全一致。

> 可选（第二节备选）：改成从 ZXDash.dll 走 C ABI 握手（照 `MhrAbi.cpp` 的
> `GetModuleHandle` + `GetProcAddress` + 主版本号模式），导出
> `ZXD_GetBiomeAbiVersion() / ZXD_BiomeAt(x,z) / ZXD_ApproxHeight(x,z,&y)`。
> 好处是算法真源只有一份；代价是要改 ZXDash（有源码，可行）并维护 ABI。
> **默认推荐内嵌同源库**：零跨插件耦合、不依赖 ZXDash 是否加载/是否被禁用。

### 4.2 预落点池（PreLandingPool）

新增 `src/PreLandingPool.cpp/.h`。池 = 两类点的集合，**总规模恒定**，是"能被 O(1) 抽出来的传送候选"。

```cpp
struct PreLanding {
    int32_t  x, z;        // 方块坐标（点本身，不是 chunk）
    int32_t  approxY;     // 未加载类：cubiomes 推算高度；已加载类：落点表给的真实 Y
    uint32_t lastUsed;    // 最近一次被命中（unix 秒，淘汰/防蹲点用）
    uint16_t biome;       // 采样到的群系 ID（诊断 + 排除复核）
    uint8_t  tier;        // 0 = 已加载类(存档内)  1 = 未加载类(需生成)
    uint8_t  state;       // 0 = 候选  1 = 已验证(可直传)  2 = 失效
};                        // 24 B/条（含对齐）；4000 条 ≈ 96 KB
```

**两类点的定义（这是最容易被误读的一处，先钉死）**：

| 类 | 定义 | 来源 | 传送时发生什么 | 默认数量 |
| --- | --- | --- | --- | --- |
| **已加载类** `tier=0` | 落点对应的 chunk **在存档里已有数据**（可能已加载，也可能只是落过盘） | 现有落点表（`ArchiveScanner`）里 `LAND_SAFE` 的点，采样 1000 个 | 走 ② 落点表零 IO 直判 → 只需把区块**载入内存**，**不生成地形** | `loadedTarget: 1000` |
| **未加载类** `tier=1` | 落点所在 chunk **存档里没有**，必然要生成 | cubiomes 按种子推算（群系 + approxY） | 走 ④ 生成路径，等 `LOAD_CHUNK` | `unloadedTarget: 3000` |

> 另一种可能的读法是"已加载/chunk 在内存 / 未加载/chunk 不在内存"，那分界线会随玩家活动漂移、
> 无法持久化。本文按**"存档里有没有"**这条稳定分界定义；如果你要的是前者，说一声，改法是把
> 判定从 `落点表命中` 换成 `isChunkReady()`，其余设计不变。

**空间索引（同时修掉 §2.2 的第 2 个弱点）**：池在内存里按 `bucketSize`（默认 512 格 ≈ 命中半径）
分桶，桶索引 `(dim, bx, bz) → 点下标数组`，只存在于内存（不落盘）。抽点从"整表拒绝采样"变成
**桶采样**，命中率与半径无关。

**自愈（池能收敛的关键）**：

| 事件 | 动作 |
| --- | --- |
| 未加载类的点被用了、生成后**扫描通过** | `state = 已验证`，`tier` 升为 0（它现在有存档数据了）→ 后台补 1 个新的未加载类点 |
| 未加载类的点生成后**整 chunk 无安全列** | `state = 失效` → 剔除 + 补新点（这就是"扫上缺少的数量"的闭环） |
| 已加载类的点连续 N 次传送失败 | `state = 失效` → 剔除 + 补新点 |
| `.ldb` 指纹变化（世界变过） | 已加载类**全部不重扫**，只把 `state` 退回"候选"，下次用到时走现有四级路径重新验证 |

`landings.cache` 那套"世界变过一次就整轮重算"的做法不复制到池上 —— 池是采样点，不是全量索引。

**持久化**：`Meowdata/Mtps/landingpool.bin` + `landingpool.bin.meta`。

```
bin : magic "MTPPOOL1" | uint32 版本 | uint32 单条大小 | 每维度: uint64 条数 + 条目数组 | CRC32
meta: seed(64位) / cubiomesMc / builtRadius / originX / originZ / loadedTarget / unloadedTarget
      / dangerBlocks 指纹 / 生成时间 / 是否待重建
```

写盘走临时文件 + 改名（与现有 `DataStore` 一致），坏了能识别（CRC）→ 重建，不会带着残文件跑。

### 4.3 群系排除

```jsonc
"excludeBiomes": [        // 按 cubiomes 群系名写，不写 ID（ID 会随 fork 漂移）
  "ocean", "deep_ocean", "frozen_ocean", "deep_frozen_ocean",
  "warm_ocean", "lukewarm_ocean", "cold_ocean",
  "deep_warm_ocean", "deep_lukewarm_ocean", "deep_cold_ocean",
  "river", "frozen_river"
],
"optionalExcludeBiomes": [ "beach", "snowy_beach", "stone_shore", "mushroom_fields" ],  // 默认关
"neighborAgreeRadius": 2   // 群系格；2 格 = 8 方块，要求 (2r+1)^2 邻域同一群系
```

三条规则：

1. **群系排除**：候选点群系 ID 命中 `excludeBiomes` → 直接丢。
2. **邻域一致性**：以候选点为中心采样 (2r+1)×(2r+1) 个群系格，必须**全部相同**才接受。
   群系边界往往就是海陆交界 / 断崖，落在这里风险最高（也是"地图上一条细线"的来源）。
3. **高度下限**：`approxY ≤ 海平面(62) + 1` 或 `> 320` → 丢（配合 §3.2 的 red line，
   只是预筛，不当作最终判定）。

> 为什么必须做排除：大半径圆盘里海洋（含深海）+ 河流占掉相当大比例的面积（数成量级）。
> 不排除的话 3000 个未加载类点会批量落在水上，每次传送都要先花几十 tick 生成一块海，
> 再扫描失败换点 —— 双向浪费。（真实比例在 P0 探针里顺手统计一下，作为默认半径下
> `unloadedTarget` 该配多少的依据。）

### 4.4 未加载类预落点的生成算法

背景线程，给定 `(originX, originZ, radius, dim, 目标数量 N)`：

```
while (点数 < N 且 尝试次数 < N * maxTriesPerPoint) {
    b = 圆盘内均匀随机一个"桶"（bucketSize 格），加权 = 桶内已有可用点数（前期无点则纯均匀）
    // 这就是"随机出大致的区域"
    (x, z) = b 内均匀随机一个方块坐标
    id = biomeAt(x, z)                       // scale=4, y=15，与 ZXDash 底图同切片
    if (id ∈ excludeBiomes) continue
    if (!neighborAgree(x, z, neighborAgreeRadius)) continue
    if (!approxHeight(y, id2, x, z))         // 一次 mapApproxHeight（w=h=4 → 覆盖 16 格）
        y = 海平面基准                          // 兜底：算不出就用基准，反正只是 hint
    if (y < 海平面+1 || y > 320) continue
    if (与已有点的距离 < minSeparation) continue     // 防扎堆
    入池(tier=1, state=候选, approxY=y, biome=id)
}
```

**`minSeparation` 是必须的**，理由见 §4.6 的密度计算：半径小的时候 3000 个点会全挤在十几个桶里，
玩家每次都被传到同一片区域。默认 `minSeparation: 64`（4 区块）。

**成本估算（待 §11 探针实测）**：单点约 9 次群系采样 + 1 次 `mapApproxHeight`，量级 10~100 µs/点；
3000 点 ≈ 亚秒~数秒，且只在**缺口**存在时跑。参考 ZXDash：256×256 瓦片（65536 格）在 k≤2 是
"毫秒级"，k=8 约 0.9 s/瓦片 —— MTPS 只要点，比出图便宜几个数量级。

### 4.5 玩家随机传送新流程

现有链路**一行不改**，只在最前面加一层"池命中"：

```
pickNewTarget(s):
  ┌─ ① 池命中（新）────────────────────────────────────────────┐
  │  池未就绪 / enabled=false / 该维度无点 → 跳过，进 ②          │
  │  p = 池.随机抽点(origin, radius, dim, rng)     // 桶采样 O(1) │
  │  命中半径内抖动: t = p + 随机偏移(≤ hitRadius=500)           │
  │    抖动后复检: 群系排除 + 邻域一致性（两次采样，微秒级）        │
  │    不合格 → 退回 p 本身                                      │
  │  s.target = t; s.hintY = p.approxY; s.src = Pool             │
  └───────────────────────────────────────────────────────────┘
  └─ ② 现有: preferKnownLandings ? tryKnownLanding : 圆盘均匀随机
  └─ ③ 生成失败重随时仍走现有 retryOrGiveUp（含"已知安全点"兜底）
```

命中之后**不改变判定逻辑**，交给现有 `resolveChunk`：

- **已加载类命中** → `resolveChunk` 在 ② 命中 `LAND_SAFE` → 零 IO 拿到真实 Y →
  `finishTeleport`；chunk 若还没在内存里，走 `LOAD_CHUNK` 等**载入**（不生成）。
  全程没有地形生成，只有"载入等待"。
- **未加载类命中** → `resolveChunk` ③ 返回 `NoData` → 现有生成路径：挂临时常加载区域 →
  等生成（`LOAD_CHUNK`，这就是唯一允许的等待）→ 就绪后 `SCAN_CHUNK` 用 `hintY` 加速真实扫描
  → 通过则传送 + 回写"已验证"，整 chunk 无安全列则扩圈/换点 + 回写"失效"。
- **池没命中 / 池未就绪 / 池为空** → **降级策略 = 现有全链路原样**（内存 → 落点表 → 存档直读 → 生成）。

> **为什么"先均匀随机点、再查 500 格邻域内有没有预落点"不能当主实现**：
> 半径 R 的圆盘面积 πR²，500 格邻域面积 π·500² ≈ 7.85e5。命中概率 ≈ N·π·500²/(πR²) = N·500²/R²。
> - R=1000, N=3000：3000·0.25 = 750 ≫ 1 → **必中**（这也是唯一好用的场景）
> - R=500000, N=3000：3000·(500/500000)² ≈ 0.003 → **300 次才中一次**，等于永远走降级
> - R=3000000, N=3000：≈ 8e-5 → 完全不可用
>
> 所以"随机出大致区域"的**区域**只能是**池自己的空间桶**（桶就是"大致区域"，点必然在桶内 ⇒
> 天然满足"500 格范围内"），而不是一个与池无关的均匀随机点。语义上你要的"优先走预落点"被完整保留，
> 且大半径下也真的能命中。若你坚持要"先均匀随机点"，做成 `sampling.mode: "point"` 备选，
> 但请默认用 `"bucket"`。

**抖动的意义**：避免同一坐标被反复落（蹲点/刷怪塔选址）。`jitter` 默认 `hitRadius`（500）。

### 4.6 开服补齐（只补缺口，不再乱扫）

```
开服 45s 后（沿用 RTP_LANDING_DEFER_SECONDS）后台线程:
  1. 读 landingpool.bin + .meta（毫秒级）
  2. 指纹校验: seed / cubiomesMc / builtRadius 与当前一致?
       不一致 → 按 §4.8 的策略（增量补齐 或 静默重建），不整表丢弃
  3. 有效点盘点: needL = max(0, loadedTarget  - count(可用 tier0))
                 needU = max(0, unloadedTarget - count(可用 tier1))
                 （"失效"点不计入，它们会在这轮被替换）
  4. needL > 0 → 从落点表/存档扫描里**只抽 needL 个**（不重扫全表）
  5. needU > 0 → cubiomes 按 §4.4 **只算 needU 个**
  6. 原子落盘 + 日志一行:
        [RTP][预落点池] L 1000/1000  U 3000/3000  本次补充 L 0 U 12  (半径 500000, seed ...)
  7. 池未就绪期间: RTP 走降级（现有全链路），功能不受影响，只是没有快路径
```

日志可见性是硬要求：**"再开服不乱扫"必须能从一行日志看懂**（本次计算量 = 缺口数）。

### 4.7 大半径静默重建（替换一半）

触发点：`Config::setPresets()` / `Config::update()` 里检测到**半径变更**（`RTP` 菜单保存预设、
或直接改 `Config.json` 后 reload）。

```
新半径 Rnew > 旧 builtRadius（或 builtRadius == 0）:
  标记 pool.rebuildPending = { Rnew, originX, originZ }   // 只标记，不阻塞表单、不提示玩家
  后台: 按新半径算 未加载类 目标数量(3000) 个新点
        新点入池时替换掉 旧未加载点的 replaceRatio(默认0.5)
        即最终 = 1500 旧点（覆盖中心密集区）+ 1500 新点（覆盖新的大范围）
  已加载类不动（已生成区域与半径无关）
  完成后落盘 + 日志: [RTP][预落点池] 半径 1000 → 3000000, 未加载类替换 1500/3000 个点

新半径 Rnew < 旧 builtRadius:
  淘汰圆外点 + 按需补足（半径变小反而需要更密）
```

**为什么"替换一半"是对的**：旧点密集在中心、新点稀疏在大范围，混合后两个尺度都有人能传到；
一次性全换会让"经常用的近处落点"消失，玩家体感像被改了机制。

**"静默"的边界**：不弹窗、不阻塞菜单保存、不喊话；但**要写日志**，且管理菜单里池的运行状态
（L/U 计数、上次补齐时间、是否待重建、命中率）要可见 —— 否则出问题无从下手。

### 4.8 开销预算（"只允许开服加载 + 区块等待"怎么保证）

| 场景 | 主线程 | 后台 |
| --- | --- | --- |
| 开服 | 0（全部延后 45s，线程 sleep + 可中断，沿用现有做法） | 读池 + 补缺口（cubiomes）≈ 毫秒~数秒 |
| 传送（池命中） | **1 次桶查找 + 最多 3 次群系采样**（抖动复检）= 微秒级 | 0 |
| 传送（生成等待） | 现有 `LOAD_CHUNK` 轮询（已是摊到多 tick 的既有预算） | 0 |
| 半径变更 | 0（只打标记） | 重算未加载类 |
| 关服 | 0 | 池落盘（走现有 `DataStore` 的收尾） |

**设计不变量（要写进代码注释 + 复核清单）**：

1. 传送路径上**禁止**调用 cubiomes 的批量接口（`genBiomes` / `mapApproxHeight`）——
   只允许 `getBiomeAt` 级别的单点采样，且只在抖动复检时（≤3 次）。
2. 传送路径上**禁止**任何存档 IO（现有直读路径已由 `RTP_IO_CHUNKS_PER_TICK = 2` 限流，
   池不绕过它）。
3. 池查询必须 O(1)（桶索引），不得退化成遍历 4000 条。
4. 池未就绪 → **直接降级**，绝不在主线程补算。

## 11. P0 探针（已执行，结果如下）

在 `plugins/ZXPanel/tools/biomeprobe/main.cpp` 现有模式旁边加了三档（工具已存在，只是没覆盖高度）：

```
biomeprobe height <seed> <mc> <blockX> <blockZ> <count> <stepBlocks> [y]
    // 方块坐标入参，打印 群系ID(scale4@y15) / 群系ID(scale1) / mapApproxHeight 近似高度 + 耗时
biomeprobe file <seed> <mc> <listFile> [neighborRadiusCells]
    // 批量对照：读 "x z [realY]" 每行一条，统计排除规则通过率与"近似高度 vs 真实 Y"偏差
biomeprobe pool <seed> <mc> <radius> <want> [minSep] [hitRadius]
    // 离线复现预落点池的生成算法（圆盘均匀撒点 + 群系排除 + 高度下限 + 最小间距），
    // 输出各阶段淘汰数、空间分布、群系分布与耗时 —— 用来定参数
```

**实测结果（种子 -6197444756905386890，mc=28 = MC_26_40）：**

| 验证项 | 结果 |
| --- | --- |
| `mapApproxHeight` 可用性 | ✅ 返回码 0（**原文档标为高风险的"该 fork 可能走不通"已排除**）：1229 个真实落点 + 6000 个随机点，失败 0 |
| 近似高度 vs 真实地表 Y | 平均绝对偏差 **6.0 格**，最大 50.1 格 → 作 `hintY`/预筛完全够用 |
| 单点成本 | **15.7 µs/点**（含两种群系采样）；3000 点全流程（含 25 格邻域）**439 ms** |
| `scale4@y15` vs `scale1@y63` 群系是否一致 | ✅ 20/20 一致（所以只需最便宜的 scale=4 采样，且与底图同切片） |
| 排除清单完整性 | ✅ 所有水域群系都能按名字命中（0/7/10/11/24/44-50 共 12 个） |
| 池生成接受率 | 52~60%（半径 500000/20000/1000 三档一致），约 1.96 次尝试/点 |

**⚠ 一处设计修正（探针推翻的假设）**：文档 §4.3 原写"邻域必须同一群系"。实测**只有 48.7% 的
真实安全落点能通过** —— 会误杀一半正常落点。改成 **"邻域内不得出现被排除群系"** 后通过率
**81.9%**，而且直接命中真实意图（别落在海边/水里），对平原↔森林这类正常群系过渡完全宽容。
代码按修正后的规则实现（`exclude + neighborClear`）。

**⚠ 一处发现（探针补充）**：`getBiomeAt(scale4, y15)` 会返回 `sulfur_caves` / `dripstone_caves` /
`snowy_slopes` 这类群系：
- **洞穴群系不是水**，绝不能加进排除清单（加了会误杀大量合法落点）；
- `snowy_slopes`(179) 这类 1.18 山地在 cubiomes-bedrock 的名字表里是空洞（`biome2str` 返回 null）。
  这不影响排除逻辑（**所有水域都有名字**），但意味着**名字表有洞 ≠ 是水**，排查时别按"未命名就怀疑"。

| --- | --- | --- | --- |

### 12.3 pick() 自检（每次建池后自动跑，不是 debug 开关）

`pick()` 一旦坏掉（例如桶索引没建起来），表现是**静默永远走降级** —— 不报错、看着正常、只是慢。
所以建池后固定跑 500 次合成抽取并打一行日志：

```
自检 dim0: 500/500 命中 (100%), 已加载类 98 / 未加载类 402;
落点距原点 平均 268757 最小 11 最大 499874（半径 500000, 应在半径内）;
抖动 平均 180 最大 500（应 ≤ 500）
```

### 12.4 实施中发现并修掉的缺陷（都是实测才暴露的）

1. **已加载类取点套了 `minSeparation`** → 落点表本身就是"每 chunk 一个点"（间距 16 格），
   再套 64 格间距把 856 个合格点砍到 110。修：已加载类不做最小间距（那个规则只服务于
   我们自己撒点的未加载类）。
2. **已加载类取点没去重** → 每次开服把同一批点再收一遍（实测 96 个重复坐标，库存虚高到 3790）。
   修：加位置哈希去重。
3. **半径缩小时区域外的点不清理** → 半径 3000000 → 500000 后留下 135 个永远抽不到的已加载点
   （最大距原点 846872）。修：两类都按目标区域清理（未加载类的清理计入"替换一半"额度，
   不重复淘汰）。

### 12.5 给你的两个实测结论（影响你怎么配）

1. **`loadedTarget: 1000` 在本服配不满**：区域（半径 500000）内共 1299 个存档落点 → 过一遍群系
   排除后只剩 **694** 个合格。日志会明说 `已加载类未配满 694: 考察 1299 个（已在池中 694 /
   新合格 0）`。想按 1000 走要么缩小半径（密度上去了），要么把 `loadedTarget` 调到 ~700，
   要么等玩家多探索（新生成的区块会自动进池）。**未加载类 3000 不受影响**，稳定配满。
2. **"随机传送落在已探索区"的概率 = `已加载/(已加载+未加载)`**：`pick` 是在所有可用点里等概率取，
   所以当前是 694/3694 ≈ **19% 落在已知安全区、81% 去新地形**。若你希望"新地形为主"，把
   `loadedTarget` 调小即可（例如 300 → 9%）。

## 13. 后续：把"随机传送很烂"拆开看（2026-10-01 晚）

反馈是"开启 debug 看不到过程 + 当前随机传送很烂"。查出四件事，三件已修、一件是死配置。

### 13.1 debug 总开关是坏的（看不到过程的直接原因）

`rtpDebugEnabled()` 只读 `randomTeleport.debug`，而 README 与 `Config.h` 都写着"顶层 `debug`
是总开关，两者任一开着都会输出"。实际情况：顶层 `debug: true` 已开，但 `randomTeleport.debug`
这个键**在配置里根本不存在**（迁移没补），于是 34 处 `[RTP]` 埋点一条都不输出。
修：两个开关取或；迁移补上 `randomTeleport.debug` 键。

### 13.2 四分之一的地图落点原本在树冠上（"烂"的最大来源）

表面扫描是"从 y=200 往下找第一个非空气方块"。树叶在基岩版是实心方块 → **整片森林的落点
都停在树冠顶**，玩家传过去站在树上，得砸树叶才下得来。

证据（存档直读 `ldbinspect surface`，出生点附近 81×81 chunk，有数据的 172,032 列）：

| 表面方块 | 列数 | 占陆地列 |
| --- | --- | --- |
| grass_block | 88,165 | 51.4% |
| short_grass | 27,538 | 16.1% |
| **树叶（oak+acacia+birch）** | **20,905** | **14.2%** |
| sand | 10,005 | 5.8% |
| 水（water+seagrass） | 28,390 | 16.5% |

逐 chunk 新旧对照（1257 个共同 chunk，都判为有安全列）：

```
Y 不变: 959 (76%)   变低: 298 (24%)   变高: 0
变低幅度: -9 格 ×28、-11×9、-10×12、-13×3、-19×2、-22/-23/-30 各 1 …（就是树冠到地面的距离）
```

**24% 的落点下移了 9~30 格。** 修法：`*_leaves` 一律不算地表（按后缀判，覆盖所有树种），
扫描时穿过它继续往下，落点取地面。三个取面点（内存 `findSurfaceSafe` / 同步存档
`scanChunkSurface` / 预计算 `decodeSubchunkColumns`）用同一套规则，并加
`kLandingRulesVersion` 让老的 `landings.cache` 与池里的"已加载类"点自动重算
（光看 `.ldb` 指纹发现不了规则变化）。

顺带确认：树叶**不能**塞进 `dangerBlocks` —— 那边的语义是"整列不要"，而树叶要的是"跳过继续找"。

### 13.3 maxAttempts 是个死配置

`randomTeleport.maxAttempts`（本服配 200）只被读取、**从未被任何逻辑使用**；真正的重试次数
写死在会话里的 `reRandomLeft = 6`。名字看着是"最多尝试几次"，配了 200 实际只试 6 次 ——
表现就是"偶尔没找到安全位置，退款"。修：按名字的意思接上，上限封 16
（每次尝试都可能生成 25 块区块，无上限会塞爆生成队列；会话 60s 超时仍是兜底）。

### 13.4 过程可见性的增强

- **`[RTP][汇总]`**：每次传送末尾一行，把过程压成结论 ——
  `候选N轮（其中池未命中M轮）| 无安全列X次 需生成Y次 扩圈最深Z圈 | 安全列来源: 内存/落点表/存档直读 各几次 | 等生成G轮`。
- **`[RTP][落点复核]`**：把落点脚下与身位的方块名打出来（`脚下=` `脚=` `头=` `头2=`）——
  一眼看出是不是落在树冠/水里；也是本次树冠修复的长期监控点。
- **池为什么没命中**：以前"池不可用"是完全静默的，现在会说明是"未启用/还没补齐/该维度没有点"
  还是"圆内没有可用预落点"。

### 13.5 "怎么要等待这么久"：13.8 秒里有 10 秒是白等的

实机日志（`BeetleCellar915` 一次传送）：

```
04.153 会话开始 → 池命中未加载类 (-261852,-375301)
04.169 存档无此 chunk → 登记常加载区域 _0
06.581 落点区块 等待48tick 状态=Loaded          ← 生成只花 2.4 秒, 而且已找到安全列 (-261855,69,-375301)
06.581 已登记常加载区域 _1（落点 (-261856,-375302)）
06.619 等待 第1tick 状态=Unloaded               ← 刚 Loaded 的区块被卸掉了！
…（状态一直卡在 StructPostProcDone）…
16.626 区块200tick未就绪, 换点重随              ← 白等 10 秒后超时
17.978 第2个候选 27tick 就绪 → 成功传送
```

**根因**：`ensureTickingArea` 用"方块坐标完全相同"判断区域是否已就位。落点是
(-261856,-375302)、区域中心是 (-261852,-375301)，差 1 格 → 判定"要换地方" → **先撤旧区域再挂新的**。
撤掉那一刻，覆盖这些区块的引用就没了，引擎当场把刚生成好的区块卸掉（日志里 `Loaded` 隔一拍变
`Unloaded`），新区域又让引擎从头加载，结果卡在 `StructPostProcDone` 直到 200 tick 超时。

代码自己在宽限期那段注释里警告过这个坑（"撤到新区域生效之间有一拍左右没有任何引用，引擎正好
可以卸掉刚加载的区块"），但 `ensureTickingArea` 还是踩了。而落点带 +0.5 偏移、`finishTeleport`
取 `floor`，所以**几乎每一次落点都会与区域中心差 1 格** —— 这条路径一直在被触发。

**修法（两处）**：

1. **区域是"圆"、有半径**：只要新区块中心到区域中心的偏移 ≤ `区域半径 − 需要半径`，就直接复用，
   不做任何登记动作。`r=2` 时即"同一个区块就复用"。
2. 真要换地方时**先挂新区域、再撤旧的**，且旧区域走宽限期队列延后 40 tick 撤
   （`RTP_AREA_HANDOVER_TICKS`）—— 新旧覆盖范围的重叠部分不会失去引用。

**效果**：该次传送的 10 秒白等消失，第 1 个候选在 2.4 秒时就能直接传送。
剩下的 1.4~2.4 秒是"在一个没生成过的地方生成一个区块"的固有成本（半径 2 的常加载区域 =
25 块），不是缺陷；要完全免等就只能落在已生成区域（池里的"已加载类"点）。

### 13.6 顺带修掉的两个连带问题

- **抖动取消**（`PreLandingPool::pick`）：以前未加载类的点会在命中半径（默认 500 格）内随机偏一下,
  偏几百格经常跨过区块边界 —— 于是真正被生成/验证的是**另一个 chunk**，而回写状态按"池点所在
  chunk"判断，**成功的传送被误判成"该 chunk 无安全列"而标记失效**（实测日志里就是这么发生的：
  传送成功，池点却被标失效，池子白白丢一个好点）。取消抖动后池点就是目标点，回写判断不再有歧义，
  还省掉主线程一次约 90µs 的群系复检。防蹲点改由"用过即升级"承担：未加载类的点一旦生成并验证
  通过就升为已加载类，不会再以"待生成候选"的身份被抽中第二次。
- **`hitRadius` 有了真正的作用**：改为"同一玩家连续两次传送的最小间隔（格）"——
  主要作用于已加载类（它们聚集在已探索区）。池里没有更远的点时自动放开约束，不会因此失败。
- **落点坐标打印统一 `floor`**：落点位置带 +0.5 偏移，负数强转会向上取整，日志里"命中安全列
  (-261855,…)"与"落点区块 (-261856,…)"差一格，读日志时极易误判。现在统一取真正所在的方块。

### 13.7 "太久了"（第二例）：传送发生在池就绪之前

实机日志（`BeetleCellar915`，开服约 43 秒时传送）：

```
03:26:33.400 [RTP][会话] 开始 … 存档就绪=否(索引建立中)
03:26:33.400 [RTP][预落点池] 不可用（未启用 / 还没补齐 / 维度0没有点）→ 本次走降级链路
03:26:33.400 [RTP][落点] #1 (116461, -174299) 距原点209626格      ← 均匀随机点
03:26:39.246 [RTP][区块就绪] 等待116tick 状态=Loaded              ← 白生成 5.8 秒
03:26:39.247 [RTP][落点判定] chunk(7278,-10894) 不安全: 内存扫:整chunk无安全列  ← 白生成的点!
03:26:39.349 [RTP][扩圈] r=1 chunk(7279,-10893) 命中安全列 (116473, 63, -174284)  脚下=sand
03:26:39.356 [RTP][结束] 耗时5956ms
```

两个问题：

1. **池当时不可用** —— 旧实现要等「45 秒延后 + 落点表就绪(还要 45 秒 + 建索引)」才建池，
   于是开服后头一分钟内的传送全都走降级路径。而**未加载类那 3000 个点压根不依赖存档**
   （纯 cubiomes 推算），没理由陪落点表一起等。
   修：池的延后从 45 秒降到 **5 秒**，并拆成两轮 ——
   第一轮不等落点表（只建未加载类，2ms 完成），落点表好了再跑第二轮补已加载类。
   实测同一轮启动：池可用时间从 `03:30:38` 提前到 **`03:29:57`（早 41 秒）**，
   池就绪延迟从"启用后 ~47 秒"降到 **~6 秒**。
   另外种子等待改成"等非 0"：极早期 Level 在、世界没加载完时种子读到 0，
   拿 0 配采样器会让整场会话的群系判断全错。

2. **降级路径完全不懂群系** —— 均匀随机点里约三成落在海洋/河流上，那种点必然要
   白生成一整个区块、再判"整块无安全列"（本例白等 5.8 秒）。本例的第 1 个候选正是如此。
   修：降级路径也做群系预筛（最多 4 次单点采样，每次约 0.1ms），筛掉的点会记一行
   `[RTP][落点] 已按群系预筛掉 N 个落点`。这样"池没就绪的那几秒"也不会再把玩家往大洋里扔。

### 13.8 还剩什么是省不掉的

即便全部修好，**落在没生成过的地形上就要等引擎生成那一个区块** ——
实测 27 / 48 / 116 tick（1.4s / 2.4s / 5.8s，随区块内容与开服负载浮动），
这是物理成本。要彻底免等只有两条路：
① 多攒"已加载类"点（随玩家探索自动增长，本服 750 → 828）；
② 后台主动预生成一部分池点的区块，并让 pick 优先选这些点 ——
   代价是持续的后台区块生成（对在意 MSPT 的服是个取舍），目前**没有**实现，需要的话再说。

### 13.9 传送期间把 MSPT 拉高：三处插件侧开销 + 一处引擎侧地板

反馈是"传送瞬间把 MSPT 拉高"。实测证据是日志里的 `[RTP][开销] 本 tick 随机传送占用 6ms`
（预算是 2ms、超 5ms 告警）以及等待期间**每拍一次全列扫描**。查下来四条，前三条是插件侧、可修：

| # | 问题 | 修法 | 效果 |
| --- | --- | --- | --- |
| 1 | 取面扫描**同一个方块查两次**（`!blockAt(y).isAir() && !isLeafAt(y)`，后者又 `blockAt` 一次）—— 这是我上一轮加"树冠透明"时引入的回退 | 合并成一次 `getBlock` 判完空气与树叶 | 每列省下 20+ 次方块查询 |
| 2 | 内存扫一块**每次都先做 64 列水域快筛**，再做主循环 —— 陆地情况下这份快筛完全白做（它是为"整块大洋"准备的） | 先扫**中心 5x5 内圈**（最多 25 列），命中即返回；没命中才走快筛 + 全列扫描 | 陆地区块扫描量大幅下降；且落点更靠近目标点（与预计算表"取离中心最近的可用列"口径一致） |
| 3 | 等待"周围区块加载完"期间**每 tick 重扫同一个区块**（你 03:27 的日志里那 12 次 `区块就绪→落点判定` 循环） | 缓存落点：同一区块 + 10 拍内复用缓存，超过 10 拍才重扫一次复核 | 等待期每拍 ~1ms 的扫描归零（最多 40 拍） |
| 4 | 顺带发现：`hintY`（上一列地表高度提示）**机制一直是死的** —— 那句更新写在 `return` 之后，永远执行不到 | 给 `ScanResult` 加 `surfaceY`（没找到站位也回填地表高度），调用方真正用上它 | 后续列的粗扫被跳过，扫描更快 |

**剩下的地板是引擎侧的，插件改不了**：传送到没生成过的地方，引擎要生成 25 个区块
（实测 1.4~5.8 秒，光照占一半），并且要把新位置的区块发给客户端。这部分 MSPT 只能靠
**降低它出现的频率**来缓解 —— 也就是 13.7 那套预热：预热过的点变成"已生成"，命中它们
只需加载；常驻点更是瞬时（区块本来就在内存里）。

### 13.10 第三轮：把"生成"整体搬到后台（常驻位按需即补）

这一轮的目标是把玩家侧的等待压到接近 0。做法只有一条，但很关键：

**预热器的常驻位一旦不满，就立刻（5 秒后）补下一个**，而不是等 `intervalSeconds`（30 秒）。
道理是：常驻点被玩家用掉一个，"补一个"的生成工作量和"玩家现场等引擎生成"是**同一份工作** ——
只是搬到了后台，由预热器挑时间做（而且它会给玩家传送让路）。玩家那一侧因此变成瞬时。

实测（同一轮）：`04:16:34 → 41 → 47 → 53`，四个常驻位按 5 秒节奏填满，之后自动切回 30 秒闲置节奏；
每个点 11~24 tick（0.55~1.2 秒）完成。玩家侧实测出现了 **`耗时66ms/2tick`** 的瞬时传送
（命中常驻/已加载点），常规落到未生成区域的仍是 1.7~2.8 秒。

**意外收获**：预热生成的区块自己会进落点表 → 池的"已加载类"从 ~828 涨到 **1000/1000 满配**
（之前是"合格点不够、配不满"）。"预热 → 池变厚 → 传送只需加载"这个闭环自己跑起来了。

**本轮还做了**：

| 项 | 内容 |
| --- | --- |
| 日志节流 | 等待期原来**每拍**打两行（一个传送几十行），改成每 5 拍一行 —— 这服的日志已经涨到 4.3GB，日志 IO 本身也在吃 MSPT |
| `randomTeleport.landingHoldTicks` | 新增可调（默认 40）：落点就绪后"周围 5x5 没加载完"最多再等多少拍。超了就照样传送（客户端随后几百毫秒补齐），**调小 = 更快** |
| 汇总行加拆分 | `[RTP][汇总]` 现在带 `等生成 N 轮 X 拍（其中等周围一圈 Y 拍）`，下一轮调参可以直接看数据 |
| 开销告警 | 上一轮 3 条（5/6/7ms）→ 本轮 1 条（5ms）；等待期每拍 ~1ms 的扫描已归零 |

**一个被证伪的假设（留个记录，免得以后再查一遍）**：怀疑"传送路径每 tick 推一次
`requestChunkLoad`（内部是 `createNewChunk`）"拖慢了生成 —— 因为预热器不调它、只要 11~24 tick，
而传送路径要 35~100 tick。做了对照实验（给预热器临时加上这个调用）：**14/19/20/22 tick**，
与不调的 **11~24 tick** 无显著差异 → 假设不成立（`getExistingChunk` 命中了就会提前返回）。
传送路径那 35~100 tick 与预热器 11~24 tick 的差距来自"有玩家在线时的服务器负载"，不是插件开销。

**剩下的可调项**（都在 `Config.json` 里）：

| 键 | 默认 | 调它的意思 |
| --- | --- | --- |
| `pool.warm.keepResident` | 4 | 常驻（瞬时）落点数量。调到 ≥ 玩家传送频率，绝大多数传送就是瞬时的；每个约占 25 个区块内存 |
| `pool.warm.intervalSeconds` | 30 | 常驻位满之后的闲置预热节奏 |
| `pool.warm.startDelaySeconds` | 90 | 开服后多久开始预热（让开服负载过去） |
| `randomTeleport.landingHoldTicks` | 40 | 邻域等待上限。想更快就调 20（代价：落点周围可能先短暂空白） |

### 13.11 第四轮：MSPT 100+ 的真凶是"落点表重建"，不是传送本身

你反馈"两次传送瞬间 MSPT 到 100+"。查日志发现关键时序：

```
04:28:07.592 [RTP][落点表] 开服已稳定, 开始重建落点表（世界改动后一次性重算）
04:28:10.520 [RTP][存档] .ldb 索引建立成功(2927ms): 19310 条 key ...
04:28:10.901 预计算进度 1945/1945 chunk（已耗时 3309ms）
```

**重建正好套在两次传送中间**（`08.3→09.667` 与 `12.944→15.598`）。而插件自身的开销日志
一条都没有（`[RTP][开销]` < 5ms），说明那 100+ms 不是传送路径花的 —— 是**落点表重建这份重活**：
读 8 个 `.ldb`、解压 19310 条 key、重算 1958 个 chunk，扫描并行度开到 6 线程，和游戏主线程抢机器。

而它为什么会跑？玩家传送会生成新区块 → `.ldb` 指纹变化 → 缓存失效 → **开服 45 秒后全量重算**，
而那时玩家已经在玩了（这也是之前所有"传送期间卡顿"的共同背景）。

**修法（三处限流 + 一处择时）**：

| 改动 | 说明 |
| --- | --- |
| 扫描并行度 6 → **2** | 这是纯 CPU+磁盘的活，索引建慢一点没关系（后台活），但不能和主线程抢机器 |
| 每个 `.ldb` 之间让出 10ms | 把突发摊平 |
| 预计算每 256 个 chunk 让出 20ms | 1958 个 chunk 只多花约 150ms，CPU 占用从"打满"降到六成 |
| **等空服再做** | 有玩家在线就每 5 秒看一眼，最多等 30 分钟；到期仍未空服则按限流模式照做。等待期用旧缓存，不影响传送 |

顺带把池服务等落点表的超时从 5 分钟放宽到 **35 分钟**（必须比"等空服 30 分钟 + 限流扫描"更长，
否则池的"已加载类"补齐会被饿死；未加载类早已就绪、不受影响）。

> 教训：`[RTP][开销]` 只覆盖插件自己的那一小段，**引擎侧与其它后台线程的开销它看不见**。
> 遇到"传送时 MSPT 高"这类反馈，先看日志里同一时间窗有没有别的大活在跑，再怀疑传送路径。

### 13.12 仍未验证的一条
`[RTP][汇总]` / `[RTP][落点复核]` 需要**真实玩家传送**才会输出，本轮只有编译期校验
（fmt 格式在编译期检查）+ 代码复核，没有实机样本。开一次 debug、在游戏里传一次，就能看到。
（13.6 的等待问题已由实机日志复现并定位，修法属于纯逻辑修复，但同样建议实机复看一次：
正常应当 2~3 秒结束，日志里不应再出现"同一区块被重新登记 + 状态从 Loaded 掉回 Unloaded"。）
